# Surv backend

FastAPI backend for Surv, with PostgreSQL 18, Redis, SQL queries generated by `sqlc`, and email OTP delivery over SMTP. The [architecture](ARCHITECTURE.md) explains the domain boundaries; [AGENTS.md](AGENTS.md) contains project rules.

Run all commands below from the `surv-backend/` directory.

## Prerequisites

- Python 3.12 or newer
- Docker with Compose
- [`dbmate`](https://github.com/amacneil/dbmate#installation) for migrations
- [`sqlc`](https://docs.sqlc.dev/en/latest/overview/install.html) for Python query generation
- An SMTP account that can send email

PostgreSQL **18** is required because the migrations use `uuidv7()` for entity IDs. The first `sqlc generate` may download the pinned Python generator specified in `sqlc.yaml`.

## First-time setup

1. Create the Python environment and install the app with development dependencies:

   ```sh
   python3 -m venv .venv
   .venv/bin/python -m pip install -e '.[dev]'
   ```

2. Create your local configuration:

   ```sh
   cp .env.example .env
   ```

   Edit `.env` before starting the API. `DATABASE_URL` and `REDIS_URL` already match the local Compose services. Replace `JWT_SECRET_KEY` with a random secret of at least 32 characters; keep the same value across API workers and restarts. Replace the SMTP placeholders with your provider's `SMTP_HOST`, `SMTP_PORT`, and `SMTP_FROM_EMAIL`. Set both `SMTP_USERNAME` and `SMTP_PASSWORD` if your SMTP server requires authentication; omit both for a relay that allows unauthenticated sending. Use `SMTP_START_TLS=true` for a STARTTLS endpoint (commonly port 587), or `SMTP_USE_TLS=true` for an implicit TLS endpoint (commonly port 465). Only one TLS mode may be enabled. `.env` is ignored by Git; keep credentials there, not in `.env.example`.

3. Start PostgreSQL and Redis, then apply migrations:

   ```sh
   make services-up
   docker compose ps
   make migrate-up
   make migrate-status
   ```

4. Generate the database query code and start the API:

   ```sh
   make sqlc-generate
   make dev
   ```

The API is at `http://localhost:8000`. Open `http://localhost:8000/docs` for request schemas and interactive routes. Check the process with:

```sh
curl http://localhost:8000/healthz
```

OTP messages go to the SMTP provider configured in `.env`. Registration and login OTPs each expire after 15 minutes. Requesting another OTP immediately replaces the previous code; there is currently no resend cooldown or invalid-attempt limit. Login verification returns a signed JWT bearer token valid for three days. Redis stores OTPs and registration validation markers, never JWTs. Registration does not issue a token.

## Authentication routes

| Route | Purpose |
| --- | --- |
| `POST /v1/auth/register/start` | Submit an email to receive a registration OTP. |
| `POST /v1/auth/register/verify` | Submit the email and six-digit OTP; mark that email as validated in Redis. |
| `POST /v1/auth/register/complete` | Submit the same email, first name, last name, and organization name. Creates the user and organization with an ADMIN membership. |
| `POST /v1/auth/login/start` | Submit an existing account email to receive a login OTP. |
| `POST /v1/auth/login/verify` | Submit the email and OTP; receive an `access_token` bearer token. |
| `GET /v1/users/me` | Read the signed-in user. |
| `GET /v1/organizations` | List the signed-in user's organizations and roles. |
| `POST /v1/projects` | Create a project with `organization_id` and `name`; requires organization membership. |
| `GET /v1/projects/{project_id}` | Read a project in one of the signed-in user's organizations. |

For a first registration, call the three `/register` routes in order using the same email in each request. Redis stores the OTP at `register:<email>` and, after verification, a 15-minute one-use marker at `register:validated:<email>`. Completion consumes the marker. To sign in, call the two `/login` routes, then send `Authorization: Bearer <access_token>` to protected routes. Protected routes verify the JWT signature and expiry and read the user ID from its `sub` claim. To sign out, the client discards its token; an issued token remains valid until its three-day expiry. No authentication cookies are set. The `/docs` UI supports the bearer token through its Authorize button.

The project table is created after the user and organization tables so its required `organization_id` foreign key can reference an organization. Members can create and read projects in their organizations; the API returns 404 for inaccessible projects.

## Working with migrations and queries

`db/migrations/` is the schema source. dbmate applies migrations to PostgreSQL; `sqlc` reads those files to understand the schema and generates Python accessors from `db/queries/<domain>/*.sql`. `sqlc` does **not** apply migrations. The Makefile disables dbmate's automatic `db/schema.sql` dump.

To add a schema change:

```sh
make migrate-new MIGRATION=describe_change
# Edit the new db/migrations/..._describe_change.sql file.
make migrate-up
make migrate-status
make sqlc-generate
```

Put forward SQL under `-- migrate:up` and reversal SQL under `-- migrate:down`. Keep migration filenames in chronological order. For a new or changed query, edit the owning domain's file in `db/queries/`, run `make sqlc-generate`, then update its repository to call the generated method. Commit migrations, query SQL, `sqlc.yaml`, and generated code together. Use `make migrate-down` only when you intentionally want to reverse the latest local migration. The Makefile defaults `PGSSLMODE` to `disable` for local Compose; override it for a hosted database, for example `make migrate-up PGSSLMODE=require`.

## Checks and local services

```sh
.venv/bin/pytest
.venv/bin/ruff check src tests
make sqlc-generate
docker compose ps
```

Use `docker compose logs postgres redis` to inspect local service failures. `docker compose down` stops the services while retaining their data volumes. If PostgreSQL already has data from version 17, upgrade that database before using the PostgreSQL 18 image; a major-version image change does not upgrade an existing data volume.
