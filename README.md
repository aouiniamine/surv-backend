# Surv backend

FastAPI backend for Surv, with PostgreSQL 18, Redis, SQL queries generated by `sqlc`, and email OTP delivery over SMTP. The [architecture](ARCHITECTURE.md) explains the domain boundaries; [AGENTS.md](AGENTS.md) contains project rules.

Run all commands below from the `surv-backend/` directory.

## Prerequisites

- Python 3.12 or newer
- Docker with Compose
- [`dbmate`](https://github.com/amacneil/dbmate#installation) for migrations
- [`sqlc`](https://docs.sqlc.dev/en/latest/overview/install.html) for Python query generation
- An SMTP account that can send email

PostgreSQL **18** is required because the migrations use `uuidv7()` for entity IDs. The first `sqlc generate` may download the pinned Python generator specified in `sqlc.yaml`.

## First-time setup

1. Create the Python environment and install the app with development dependencies:

   ```sh
   python3 -m venv .venv
   .venv/bin/python -m pip install -e '.[dev]'
   ```

2. Create your local configuration:

   ```sh
   cp .env.example .env
   ```

   Edit `.env` before starting the API. `DATABASE_URL` and `REDIS_URL` already match the local Compose services. Replace `JWT_SECRET_KEY` with a random secret of at least 32 characters; keep the same value across API workers and restarts. Replace the SMTP placeholders with your provider's `SMTP_HOST`, `SMTP_PORT`, and `SMTP_FROM_EMAIL`. Set both `SMTP_USERNAME` and `SMTP_PASSWORD` if your SMTP server requires authentication; omit both for a relay that allows unauthenticated sending. Use `SMTP_START_TLS=true` for a STARTTLS endpoint (commonly port 587), or `SMTP_USE_TLS=true` for an implicit TLS endpoint (commonly port 465). Only one TLS mode may be enabled. Set `CORS_ORIGINS` to the allowed browser origins when the client and API run on different origins. `.env` is ignored by Git; keep credentials there, not in `.env.example`.

3. Start PostgreSQL and Redis, then apply migrations:

   ```sh
   make services-up
   docker compose ps
   make migrate-up
   make migrate-status
   ```

4. Generate the database query code and start the API:

   ```sh
   make sqlc-generate
   make dev
   ```

The API is at `http://localhost:8000`. Open `http://localhost:8000/docs` for request schemas and interactive routes. Check the process with:

```sh
curl http://localhost:8000/health
```

OTP messages go to the SMTP provider configured in `.env`. Registration and login OTPs each expire after 15 minutes. Requesting another OTP immediately replaces the previous code; there is currently no resend cooldown or invalid-attempt limit. Registration completion and login verification return a signed JWT bearer token valid for three days and the logged-in user's details. Redis stores OTPs and registration validation markers, never JWTs.

## Working with migrations and queries

`db/migrations/` is the schema source. dbmate applies migrations to PostgreSQL; `sqlc` reads those files to understand the schema and generates Python accessors from `db/queries/<domain>/*.sql`. `sqlc` does **not** apply migrations. The Makefile disables dbmate's automatic `db/schema.sql` dump.

To add a schema change:

```sh
make migrate-new MIGRATION=describe_change
# Edit the new db/migrations/..._describe_change.sql file.
make migrate-up
make migrate-status
make sqlc-generate
```

Put forward SQL under `-- migrate:up` and reversal SQL under `-- migrate:down`. Keep migration filenames in chronological order. For a new or changed query, edit the owning domain's file in `db/queries/`, run `make sqlc-generate`, then update its repository to call the generated method. Commit migrations, query SQL, `sqlc.yaml`, and generated code together. Use `make migrate-down` only when you intentionally want to reverse the latest local migration. The Makefile defaults `PGSSLMODE` to `disable` for local Compose; override it for a hosted database, for example `make migrate-up PGSSLMODE=require`.

## Checks and local services

```sh
.venv/bin/pytest
.venv/bin/ruff check src tests
make sqlc-generate
docker compose ps
```

Use `docker compose logs postgres redis` to inspect local service failures. `docker compose down` stops the services while retaining their data volumes. If PostgreSQL already has data from version 17, upgrade that database before using the PostgreSQL 18 image; a major-version image change does not upgrade an existing data volume.

## Static application uploads

Creating a project creates `./uploads/projects/<public_id>/public` (relative to the backend process directory) with status `CREATED`. Set `PROJECT_UPLOADS_ROOT` to use a persistent shared volume in deployment. Admins and developers can replace a project's static site with `PUT /v1/projects/<public_id>/app`, using a bearer token and a raw `application/zip` request body. The ZIP must contain `index.html` at its root. The upload limit is 20 MiB compressed, 1 GiB extracted, and 10,000 entries. Extraction rejects traversal paths and symlinks and publishes only after validation succeeds. A successful upload changes status to `DEPLOYED`. Replacing a deployed app moves its previous ZIP into `backups/` under the project storage directory and records its relative path in `project_backup`. The newest three backups per project are retained; older files and rows are removed.

The site is public at `/app/<public_id>/`. Existing files and directory indexes are served directly; other paths fall back to the site's root `index.html` for client-side routing. Build applications with relative asset URLs or with `/app/<public_id>/` as their base path.

For development path hosting, the server also maps root-relative references to uploaded static files in HTML, JavaScript, and CSS onto `/app/<public_id>/`. This lets builds that reference `/assets/...` load their files without a separate build base. Requests for missing files return 404 instead of the SPA page. Project members can list backup metadata with `GET /v1/projects/<project_id>/backups`. Each backup's `preview_url` serves its saved site at `/app-backups/<public_id>/<backup_key>/`.

Project responses include `status` and `app_url`; the client shows the URL only when status is `DEPLOYED`. With `PROJECT_ENVIRONMENT=development` (or `dev` or `staging`), the URL uses the API request origin and `/app/<public_id>/`. With `PROJECT_ENVIRONMENT=production`, set `APPS_DOMAIN=example.com` (or `*.example.com`) to return `https://<public_id>.example.com/`. The upload response uses the same URL. Production routing and wildcard DNS/TLS must direct these hostnames to the uploaded app storage.
